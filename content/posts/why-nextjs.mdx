# 为什么我的博客选择了 Next.js

## 前言

我是一个全栈程序员，已经尝试过各种框架来制作我的博客，包括但不限于 Vitepress、Halo、Astro 等。最终，我选择了 我最为熟悉的 Next.js 作为我的博客框架。接下来，我将解释为什么我选择了 Next.js。

```tsx
#!/app/page.tsx
export default function RootPage() {
  return <>Hello Next.js🎉</>
}
```

## 我排除的选项

### 为什么不是0代码的 Halo

Halo 是一个基于 Java 的博客框架，它提供了丰富的功能和强大的扩展性。然而，我并不喜欢 Java，因为它太重了，而且我并不希望将这么庞大的博客应用部署在服务器并进行维护，那简直是噩梦。

另外，样式想自定义样式极度复杂，要么自己写一个完整的主题出来，要么使用别人写好的主题去继承那些令人头皮发麻的css 类名与变量——因为他们根本不使用Tailwindcss！！！

### 为什么不是元数据驱动的 Vitepress

Vitepress 是一个基于 Vue 的静态网站生成器，它提供了极佳的 SSG 静态文档生成水平。理论上来说，他可以完全基于纯静态的 Markdown 文件生成一个静态网站，而不需要任何后端服务。

但是，缺陷也在这里，我的博客依赖不少动态的后端服务，比如评论系统、文章的阅读量统计、文章的点赞、文章的分享等等。这些功能虽然在 Vitepress 中也可以变着法实现，但是需要大量的自定义代码，而且性能也会变得相当羸弱。

## 是什么让 Next.js 牢牢吸引了我

### 丰富的功能

Next.js 提供了丰富的功能，包括但不限于：

- **静态网站生成（SSG）**：Next.js 可以将你的页面预渲染为 HTML，从而提高网站的加载速度和 SEO。
- **服务器端渲染（SSR）**：Next.js 可以在服务器端渲染你的页面，从而提高网站的响应速度和用户体验及SEO水平。
- **React服务端渲染（RSC）**：Next.js 可以将你的 React 组件在服务器端渲染，从而达成高效的水合性能。
- **部分预渲染（PPR）**：面对动态的数据，再也不用对着他们发愁。Next.js 让动态部分 Suspense，再通过流式渲染出来。或者你可以直接进行 Cache。

### 极其灵活的配置

在 Next.js 中，我可以集成几乎任何我需要的库和框架，包括但不限于：

- 3D场景构建：Three.js、R3F
- ...

### 灵活的客户端组件

在 Next.js 中，我不止能写服务端组件，客户端组件也是信手拈来。那些事件驱动或者是拥有状态的组件只需要添加一个 `'use client'` 标识就可以了，剩下的全部交给 Next.js，他会帮你完成复杂的水合工作。

### 优秀的 Agents 能力

Next.js 提供了优秀的 Agents 能力，包括但不限于他们的 MCP、Skills、Agents.md。
